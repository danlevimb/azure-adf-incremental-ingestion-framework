# ADLS Folder Structure

## Project

`azure-adf-incremental-ingestion-framework`

## Purpose

This document describes the Azure Data Lake Storage Gen2 folder structure used by the ADF Incremental Ingestion Framework.

The folder structure is designed to support:

- Clear source-to-target traceability
- SQL Server incremental extraction outputs
- CSV and JSON file ingestion
- Run-level isolation
- Evidence-based validation
- Future extensibility toward Silver and Gold layers

---

## Storage Account

The project uses Azure Data Lake Storage Gen2 as the target storage platform.

Development storage account used during implementation:

```text
stgadfingdan01
```

The storage account contains the containers required by the framework.

---

## Containers

The approved ADLS Gen2 containers are:

| Container | Purpose |
|---|---|
| `landing` | Source landing area for file-based inputs such as CSV and JSON. |
| `bronze` | Main target zone for SQL extraction outputs and copied file-based inputs. |
| `rejected` | Reserved for rejected files or records in future validation scenarios. |
| `metadata` | Reserved for operational metadata extracts or metadata exports. |
| `evidence` | Reserved for evidence artifacts when required. |

---

## Container Strategy

The MVP focuses primarily on:

```text
landing
bronze
```

The remaining containers are included to make the structure closer to a professional ingestion framework and to allow future enhancements.

| Container | MVP Usage |
|---|---|
| `landing` | Used for source CSV and JSON files. |
| `bronze` | Used for SQL Parquet outputs and copied CSV/JSON files. |
| `rejected` | Created but reserved for future validation/error handling. |
| `metadata` | Created but reserved for future operational exports. |
| `evidence` | Created but mainly documented through the GitHub evidence folder. |

## SQL Server Output Structure

SQL Server extraction outputs are written into the `bronze` container.

General pattern:

```text
bronze/sqlserver/<source_system>/<schema>/<table>/load_date=YYYY-MM-DD/run_id=<run_id>/<table>.parquet
```

Example:

```text
bronze/sqlserver/sales_local/dbo/orders/load_date=2026-05-15/run_id=<guid>/orders.parquet
```

---

## SQL Output Path Components

| Path Component | Meaning |
|---|---|
| `bronze` | ADLS Gen2 target container. |
| `sqlserver` | Indicates the source technology. |
| `<source_system>` | Logical source system name, such as `sales_local`. |
| `<schema>` | Source SQL schema, such as `dbo`. |
| `<table>` | Source table name, such as `orders`. |
| `load_date=YYYY-MM-DD` | Processing date partition. |
| `run_id=<run_id>` | Run-level folder tied to the ingestion execution. |
| `<table>.parquet` | Output file generated by the Copy Activity. |

---

## SQL Output Format

SQL extraction outputs are written as:

```text
Parquet
```

Parquet was selected because it is a common analytical file format for lake-based data engineering workflows.

The MVP does not perform Silver or Gold transformations yet, but Parquet output in Bronze creates a stronger foundation for future downstream processing.

## File-Based Landing Structure

CSV and JSON source files are placed in the `landing` container.

General pattern:

```text
landing/files/<format>/<source_object>/<file_name>
```

CSV examples:

```text
landing/files/csv/currency_rates/currency_rates.csv
landing/files/csv/country_currency/country_currency.csv
```

JSON examples:

```text
landing/files/json/source_system_metadata/source_system_metadata.json
landing/files/json/manual_adjustments/manual_adjustments.json
```

---

## File-Based Bronze Structure

File-based sources are copied from `landing` into `bronze`.

General pattern:

```text
bronze/files/<format>/<source_object>/load_date=YYYY-MM-DD/run_id=<run_id>/<file_name>
```

CSV examples:

```text
bronze/files/csv/currency_rates/load_date=YYYY-MM-DD/run_id=<run_id>/currency_rates.csv
bronze/files/csv/country_currency/load_date=YYYY-MM-DD/run_id=<run_id>/country_currency.csv
```

JSON examples:

```text
bronze/files/json/source_system_metadata/load_date=YYYY-MM-DD/run_id=<run_id>/source_system_metadata.json
bronze/files/json/manual_adjustments/load_date=YYYY-MM-DD/run_id=<run_id>/manual_adjustments.json
```

---

## Why Use `load_date`

The `load_date` folder captures the processing date of the ingestion run.

Benefits:

- Makes outputs easier to browse
- Supports partition-style organization
- Helps separate daily execution outputs
- Makes evidence easier to validate visually
- Creates a foundation for future lifecycle management

Example:

```text
load_date=2026-05-15
```

---

## Why Use `run_id`

The `run_id` folder creates execution-level isolation.

Benefits:

- Prevents outputs from different runs from overwriting each other
- Connects ADLS files to ADF and control table execution logs
- Supports troubleshooting
- Supports retry analysis
- Makes evidence traceable

Example:

```text
run_id=manual-retry-after-failure
```

or:

```text
run_id=<ADF-generated-guid>
```

---

## Source-to-Target Traceability

The folder structure is designed so that a reviewer can infer:

| Question | Answered By |
|---|---|
| What source system produced the data? | `sqlserver/<source_system>` or `files/<format>` |
| Which SQL schema/table was copied? | `<schema>/<table>` |
| Which file object was copied? | `<source_object>` |
| When was it loaded? | `load_date=YYYY-MM-DD` |
| Which run produced it? | `run_id=<run_id>` |
| What format was written? | File extension or destination format metadata |

---

## Control Metadata Relationship

The ADLS path is driven by control metadata.

Relevant columns in `ctl.SourceObject` include:

| Column | Purpose |
|---|---|
| `SourceSystemName` | Used to build source-system-level folders. |
| `SourceSchema` | Used for SQL schema-level folders. |
| `SourceObjectName` | Used for table or file-object folders. |
| `DestinationContainer` | Defines the ADLS target container. |
| `DestinationFolder` | Defines the base target folder. |
| `DestinationFormat` | Defines expected output format. |

For file sources, `ctl.FileSourceConfig` provides source file path and file pattern configuration.

## Cleanup Strategy

Generated development/test outputs can be cleaned from ADLS Gen2 when needed.

The public repository includes a cleanup script:

```text
scripts/cleanup/01_clean_adls_test_outputs.ps1
```

The cleanup script is parameterized and uses ADLS Gen2 directory deletion for hierarchical namespace-enabled storage accounts.

Example cleanup command pattern:

```powershell
az storage fs directory delete `
    --account-name <STORAGE_ACCOUNT_NAME> `
    --account-key <STORAGE_ACCOUNT_KEY> `
    --file-system bronze `
    --name "sqlserver/sales_local/dbo/orders" `
    --recursive `
    --yes
```

The cleanup script should only be used in development or test environments.

## Design Value

The ADLS folder structure provides:

- Clear landing and bronze separation
- SQL and file ingestion organization
- Source-system traceability
- Run-level isolation
- Load-date organization
- Evidence-friendly validation
- A foundation for future Silver and Gold processing

This structure keeps the MVP practical while still following patterns commonly seen in professional data lake ingestion workflows.
